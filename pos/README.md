## Логика решений

### Доменная модель

- `Student` - entity: студента определяет `studentId`, имя может совпадать у разных людей.
- `Criterion` - value object: название, максимальный балл, вес в итоге.
- `Rubric` - агрегат: единственный владелец списка критериев, охраняет уникальность названий.
- `Score` - value object: балл вместе с максимумом критерия.
- `Evaluation` - entity: факт «этому студенту по этому критерию поставили такой балл».

`Student`, `Criterion`, `Score` и `Evaluation` сделаны record'ами с валидацией в компактном конструкторе: создать `Score` вне диапазона `[0, maxValue]` физически невозможно, поэтому «12 из 10» отсекается на границе домена. `Rubric` - обычный класс, не record: он мутабельный (критерии добавляются и удаляются) и как агрегат сам следит за своим инвариантом. `Evaluation` создаётся только через `EvaluationFactory`: фабрика проверяет, что критерий есть в рубрикаторе, и подставляет его максимум в `Score`, так что инварианты нельзя обойти снаружи.

Идентичность `Evaluation` - пара (`studentId`, `criterionName`), поэтому исправление оценки это повторное выставление с тем же ключом, а отмена это удаление по нему. Итог сознательно не хранится, а пересчитывается из текущих оценок и текущего рубрикатора при каждом запросе: он всегда согласован с данными, и отдельный инвариант «итог соответствует оценкам» не нужен.

### Сервисы

- `TotalCalculator` - domain service: правило итога не принадлежит ни одной сущности, оно связывает рубрикатор и набор оценок студента.
- `ITotalPolicy` , `WeightedTotalPolicy` / `SimpleSumTotalPolicy` - стратегии правила итога, калькулятор делегирует им подсчёт и сам правила не знает.
- `EvaluationFactory` - единая точка создания `Evaluation` со всеми проверками.
- `PosFacade` - фасад application-слоя: все сценарии UI (студенты, рубрикатор, оценки, ведомость) идут через него, консоль не знает про репозитории, фабрику и адаптеры форматов.
- Пары экспортёр/импортёр для CSV и JSON - адаптеры выгрузки; каркас импорта общий (`AbstractGradeSheetImporter`), различается только разбор формата.

По умолчанию итог взвешенный: `10 * sum(score / max * вес) / sum(веса)`, критерий без оценки считается нулём. Это осознанный выбор в пользу честной десятибалльной шкалы; сырая сумма баллов тоже есть как вторая стратегия и подменяется в `Main` одной строкой. Методы фасада `attempt*` возвращают причину отказа или `null` при успехе: UI не ловит исключения домена ради отказов.

Домен не знает про CSV, JSON и файлы: репозитории это порты домена, порты выгрузки (`IGradeSheetExporter`, `IGradeSheetImporter`) лежат в application, а на границе ходят только DTO (`GradeSheet`, `GradeSheetRow`, `ImportedSheet`, `ImportedGrade`). Ведомость выгружается вместе с параметрами критериев (max, вес), поэтому при импорте недостающие критерии и студенты досоздаются автоматически: ведомость можно выгрузить, очистить приложение и восстановить один в один. Для чужих файлов без метаданных критерий создаётся с параметрами по умолчанию (max 10, вес 1) и пометкой в отчёте. Внешние библиотеки не подключены, поэтому JSON разбирается своим мини парсером `SimpleJson`.

### DI-контейнер

Регистрация синглтонов и ленивых фабрик, `resolve` по типу. Вся сборка графа зависимостей в `Main` (composition root): какая стартегияитога, какие реализации репозиториев, какие форматы выгрузки. Подмена любой зависимости - одна строка в `Main`, домен и UI не правятся.

### UI

- `DemoScenarios` - сквозная демонстрация при старте: студенты, рубрикатор, оценки, проверка инвариантов, итоги, исправление и отмена оценки, экспорт в CSV и JSON.
- `ConsoleApp` - интерактивное меню, работает только через `PosFacade`. Студенты и критерии выбираются по номеру из нумерованных списков (у критерия видны max балл и вес), ID и названия вручную вводить не нужно.

## Карта DDD

| Термин (UL) | Тип DDD | Код | Комментарий |
| --- | --- | --- | --- |
| Студент | Entity | `domain/student/Student` | идентичность - `studentId` |
| Критерий | Value Object | `domain/rubric/Criterion` | название, max, вес; равенство по значению |
| Рубрикатор | Aggregate | `domain/rubric/Rubric` | инвариант: уникальность названий |
| Балл | Value Object | `domain/evaluation/Score` | инвариант: `score принадлежит [0, max]` |
| Оценка | Entity | `domain/evaluation/Evaluation` | идентичность - пара (студент, критерий) |
| Итог | Domain Service | `domain/service/TotalCalculator` | считается, а не хранится |
| Студенты / рубрикатор / оценки | Repository (порт) | `domain/repository/*` | реализации снаружи домена |
| Выставление оценки | Factory | `domain/evaluation/EvaluationFactory` | описание в паттернах |

Почему такое разделение: у `Student` и `Evaluation` есть жизненный цикл и идентичность (оценку исправляют, студента ведут по ID), а `Score` и `Criterion` - чистые значения, их подмена равнозначным объектом ничего не меняет.

## Архитектура

Облегчённая версия  **Ports & Adapters**.

```
src/main/java/pos/
├── domain/                 # центр: entities, VO, агрегат, инварианты
│   ├── student/            # Student
│   ├── rubric/             # Criterion, Rubric (агрегат)
│   ├── evaluation/         # Score, Evaluation, EvaluationFactory
│   ├── service/            # TotalCalculator + ITotalPolicy (стратегии)
│   └── repository/         # порты: StudentRepository, RubricRepository,
│                           #   EvaluationRepository
├── application/            # сценарии
│   ├── PosFacade           # единая точка входа для UI
│   └── port/               # порты выгрузки + DTO (GradeSheet, ImportedGrade)
├── infrastructure/         # адаптеры
│   ├── memory/             # in-memory реализации репозиториев
│   ├── exporter/           # CSV/JSON экспорт
│   ├── importer/           # CSV/JSON импорт (Template Method)
│   └── json/               # SimpleJson - ручной мини-парсер
├── di/Container            # DI-контейнер
├── ui/                     # ConsoleApp, DemoScenarios
└── Main                    # composition root
```

**Стрелка зависимостей - только внутрь:**

| Слой | Ответственность | Зависит от |
| --- | --- | --- |
| `domain` | модель, инварианты, порты | ни от чего |
| `application` | сценарии, DTO, порты выгрузки | `domain` |
| `infrastructure` | хранение, файлы, форматы | `domain`, `application` (реализует их порты) |
| `ui` | ввод-вывод | `application`, `domain` (только чтение для вывода) |
| `di` + `Main` | сборка графа зависимостей | всех; от него не зависит никто |

Инфраструктура зависит от абстракций (портов), а не наоборот: домен не
импортирует ни одного класса из `infrastructure` или `ui`.

## Паттерны GoF

| Паттерн | Группа | Где | Какую боль закрывает |
| --- | --- | --- | --- |
| **Factory** | порождающие | `EvaluationFactory` | единая точка создания `Evaluation`: проверка критерия в рубрикаторе и подстановка его максимума в `Score` - инварианты нельзя обойти снаружи |
| **Facade** | структурные | `PosFacade` | консоль не знает про 3 репозитория, фабрику, калькулятор и 4 адаптера форматов - сценарии не в UI |
| **Strategy** | поведенческие | `ITotalPolicy` + `WeightedTotalPolicy` / `SimpleSumTotalPolicy` | правило итога сменяемо; подмена - одна строка в `Main`, домен не правится |
| **Template Method** | поведенческие | `AbstractGradeSheetImporter` + `CsvGradeSheetImporter` / `JsonGradeSheetImporter` | каркас импорта (файл -> текст -> запись -> «не пусто») общий, различается только разбор формата |

## Запуск

### Требования

- JDK 17 или выше (record, switch-выражения, text blocks).
- Maven.

### Через IntelliJ IDEA

1. Открыть `Main.java` и нажать **Run 'Main.main()'**.

### Через Maven

```
mvn clean compile exec:java -Dexec.mainClass="pos.Main"
```

### Что происходит при запуске

1. **Демонстрация.** Сквозной сценарий: заводим студентов и рубрикатор, выставляем оценки, проверяем инварианты, итоги,  исправление и отмена оценки, экспорт ведомости в CSV и JSON (`exports/`).
2. **Очистка.** После демонстрации все данные очищаются.
3. **Интерактивное меню.** Пользователь работает с нуля.

### Меню

```
=== ПОС ===
1. Добавить студента
2. Добавить критерий в рубрикатор
3. Список студентов
4. Рубрикатор
5. Выставить/исправить оценку
6. Отменить оценку
7. Оценки студента
8. Итоги по всем студентам
9. Экспорт ведомости (csv/json)
10. Импорт ведомости (csv/json)
0. Выход
```

При выставлении и отмене оценки студент и критерий выбираются **по номеру** из нумерованных списков (у критерия видны max балл и вес) - ID и названия вручную вводить не нужно. Просмотр оценок студента (пункт 7) работает так же.

## Тесты

Запуск всех тестов:

```
mvn clean test jacoco:report
```

Или в IDEA: `src/test/java` → **Run 'All Tests'**.

### Что покрыто

31 тест, покрытие **>70%** (за исключением `ui` и `Main` - там только ввод-вывод):

- **Инварианты:** `ScoreTest` (диапазон балла), `RubricTest`
  (уникальность критериев, валидация параметров), `EvaluationFactoryTest`
  (критерий обязан быть в рубрикаторе, балл - в диапазоне критерия).
- **Domain Service:** `TotalCalculatorTest` - взвешенный итог по формуле,
  непроставленный критерий = 0, подмена стратегии меняет результат,
  чужие оценки не учитываются.
- **Сценарии:** `PosFacadeTest` - дубликаты, отказы, исправление/отмена
  оценки, согласованность итога.
- **Template Method:** `GradeSheetImporterTest` - round-trip
  «экспорт CSV/JSON -> импорт» даёт одинаковые записи; битый файл и
  пустой файл отклоняются; сквозной сценарий «выгрузить -> очистить ->
  импортировать» восстанавливает студентов, критерии и итог один в один.

### Подмена зависимостей

Всё через конструкторы: `TotalCalculator` принимает `ITotalPolicy`,
`PosFacade` - репозитории, фабрику, калькулятор и списки адаптеров.
Тест `policySwapViaConstructor_changesTotal` собирает два фасада
с разными политиками и показывает разный итог на одних данных.
