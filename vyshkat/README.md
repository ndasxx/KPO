## Логика решений

### Доменная модель

- **`IInventoryItem`** - общий контракт для всего, что ставится на баланс:
  инвентарный номер, наименование, тип.
- **`IEnergyConsumer`** - контракт для всего, что потребляет энергию:
  суточный расход в кВт·ч.
- **`IVehicle`** - транспорт, наследник обоих интерфейсов. Дополнительно
  знает свою «простоту для новичка» (1-10) и умеет отвечать, подходит ли
  новичку.
- **`IThing`** - вещи на балансе (шлемы, зарядные станции, док-станции).
  Наследует только `IInventoryItem`.

Конкретные классы (`Scooter`, `Bicycle`, `ElectricBike`, `Helmet`,
`ChargingStation`, `DockingStation`) реализованы как **record** - это
неизменяемые value-объекты, у которых `equals`, `hashCode`, `toString`
генерируются автоматически. Валидация физических инвариантов выполняется
в компактном конструкторе record (например, `beginnerFriendliness` должен
быть в диапазоне 1..10, `dailyEnergyKwh ≥ 0`, непустой инвентарный
номер).

`Bicycle` возвращает `0.0` из `dailyEnergyKwh()`- велосипед энергии не
потребляет, но участвует в общей модели транспорта. Это осознанное решение: вводить отдельный `IElectricVehicle` 
ради одного случая как-то не оч.

### Сервисы

- **`ServiceCenter`** реализует `ITechnicalInspection` и решает, принять
  ли транспорт в парк. Проверяет бизнес-правила: непустое имя, разумный расход энергии и простота 
  для новичков(если <2, техосмотр не будет пройден).
- **`Fleet`** - учёт парка. Принимает транспорт только после техосмотра,
  проверяет уникальность инвентарного номера ( и среди транспорта, и среди вещей), умеет удалять и 
  очищать парк, считает суммарное энергопотребление и отдаёт список техники для новичков.

Создание транспорта и вещей по коду типа выполняется прямо в UI-слое
(`ConsoleApp` и `DemoScenarios`) через `switch`. Для трёх типов транспорта
и трёх типов вещей это проще, чем вводить отдельные фабрики: `switch`
живёт в одном месте UI, а `Fleet` работает с абстракциями `IVehicle` /
`IThing` и не знает о конкретных классах.

### DI-контейнер

**`Container`** - контейнер зависимостей.
Реализованы `register` (singleton) и `registerFactory` (ленивое создание
с кэшированием). Собирает граф зависимостей в `Main`.

### UI

- **`DemoScenarios`** - автоматическая демонстрация всех сценариев. При запуске приложение прогоняет её перед интерактивной частью.
- **`ConsoleApp`** - интерактивное меню. После демонстрации парк
  очищается, пользователь работает с нуля.

## Архитектура

```
src/main/java/vshkat/
├── domain/
│   ├── IInventoryItem
│   ├── IEnergyConsumer
│   ├── IVehicle
│   ├── IThing
│   ├── vehicle/          # Scooter, Bicycle, ElectricBike
│   └── thing/            # Helmet, ChargingStation, DockingStation
├── service/
│   ├── ITechnicalInspection
│   ├── ServiceCenter
│   └── Fleet
├── di/
│   └── Container
├── ui/
│   ├── DemoScenarios
│   └── ConsoleApp
└── Main
```

**Правило зависимостей:** `ui -> service -> domain`.
`di` зависит от всех, но от него никто не зависит, кроме `Main`.

| Пакет | Ответственность | Зависит от |
|---|---|---|
| `domain` | Абстракции и value-объекты | ни от чего |
| `service` | Бизнес-логика | `domain` |
| `di` | Сборка графа зависимостей | всех |
| `ui` | Ввод-вывод и создание объектов | `service`, `domain` |

## Запуск

### Требования

- JDK 17 или выше (используются `record`, `instanceof` и switch-выражения).
- Maven.

### Через IntelliJ IDEA
1. Открыть `Main.java` и нажать **Run 'Main.main()'**.
### Через Maven

```bash
mvn clean compile exec:java -Dexec.mainClass="vshkat.Main"
```

### Что происходит при запуске

1. **Демонстрация.** Приложение автоматически прогоняет все
   сценарии: добавление транспорта, добавление вещей, техосмотр
   (принять/отклонить), отчёт по энергии, список для новичков, вывод
   инвентарных номеров, удаление, отказ из-за дубликата.
2. **Очистка парка.** После демонстрации парк обнуляется.
3. **Интерактивное меню.** Пользователь работает с пустого
   парка.

### Меню

```
=== ВышКат ===
1. Принять транспорт в парк
2. Принять вещь на баланс
3. Отчёт: число единиц и суммарная энергия
4. Список техники для новичков
5. Все инвентарные номера (техника + вещи)
6. Удалить транспорт по инвентарному номеру
7. Удалить вещь по инвентарному номеру
0. Выход
```

## Ответы на вопросы

### 1. Какой принцип SOLID применён наиболее явно и где?

**Dependency Inversion Principle (DIP).**

`Fleet` зависит от интерфейса `ITechnicalInspection`, а не от конкретной реализации
`ServiceCenter`.

Также явно применён **Single Responsibility**: валидация данных лежит в `record`, `ServiceCenter` -
техосмотр, `Fleet` - учёт, `DemoScenarios` - демонстрация сценариев,
`ConsoleApp` - интерактивное меню, `Container` - DI. Ни один класс не
смешивает эти обязанности.

### 2. Какой принцип сознательно ограничен / «почти нарушен» и почему это приемлемо?

**Open/Closed Principle - ограничен в `ConsoleApp` и `DemoScenarios`.**

При добавлении нового вида транспорта приётся
править `switch` по типам в `ConsoleApp.addVehicleInteractive()` и в
`DemoScenarios`. Формально это нарушение OCP: класс открыт для
модификации.

Почему это приемлемо:

- `switch` находится в **UI-слое**. `Fleet`, `ServiceCenter`,
  `domain`-интерфейсы, `Main`, `Container` - не меняются. Главное
  правило OCP соблюдено: бизнес-логика не знает о конкретных типах.
- UI обязан знать о конкретных типах, чтобы запросить у пользователя правильные параметры 
  (например, спросить про энергию только у электротранспорта). 
- Вынесение этого в абстрактную фабрику создало бы избыточный слой кода без реальной пользы. 
  При этом `Fleet`, `ServiceCenter` и интерфейсы остаются полностью закрытыми для модификации и открытыми для расширения.

**Interface Segregation - тоже ограничен.** `IVehicle` требует
`dailyEnergyKwh()`, и `Bicycle` обязан вернуть `0.0`. По ISP
нужно было бы разделить `IVehicle` на `IMotorVehicle` и `IVehicle`, но
это создало бы дополнительные абстракции ради одного случая (при расширении программы это имеет смысл).

### 3. Что сломается при добавлении нового вида транспорта, сотрудника или склада запчастей?

**Новый вид транспорта (например, `Moped`).**

Не сломается ничего критичного. Нужно:
1. Создать `domain/vehicle/Moped.java` - record, реализующий `IVehicle`.
2. Добавить одну константу `VEHICLE_TYPE_MOPED` в `ConsoleApp` и по
   одному `case` в `switch` внутри `ConsoleApp.addVehicleInteractive()`
   и `DemoScenarios` (если нужно показать новый тип в демо).

`Fleet`, `ServiceCenter`, `Container`, `Main`, все интерфейсы и
record - **не меняются**.

**Сотрудник (`Employee`).**

Сотрудники не ставятся на баланс(по тз), поэтому `Employee` не должен
реализовывать `IInventoryItem`. Сценарий расширения:

1. Создать `domain/employee/Employee.java` - отдельный record.
2. Создать `service/EmployeeService.java` - отдельный сервис.
3. Зарегистрировать в `Container` и добавить пункт в `ConsoleApp`.

`Fleet` не меняется, потому что работает только с `IVehicle` и `IThing`.

**Склад запчастей (`SparePart`).**

Запчасти могут быть инвентаризируемыми, тогда:

1. `domain/thing/SparePart.java` - record, реализующий `IThing` (если
   нужно учитывать на балансе) или отдельный интерфейс.
2. Если реализует `IThing` - добавить `case` в `ConsoleApp.addThingInteractive()`.
3. `Fleet` не меняется: `addThing` принимает `IThing`.

Если запчасти требуют отдельного учёта (например, по модели и количеству,
а не по уникальному номеру) - вводится отдельный сервис `WarehouseService`. `Fleet` и
`ConsoleApp` не трогаются, добавляется новый пункт меню.

**Вывод:** Единственное место, которое
придётся править при добавлении типа транспорта или вещи - UI-слой
(`ConsoleApp` и, при необходимости, `DemoScenarios`). Бизнес-логика
(`Fleet`, `ServiceCenter`) не меняется вообще.

### 4. Какой тест фиксирует решение техосмотра и/или правило «для новичков»? Как подменяется зависимость?

**Решение техосмотра:**

Тест rejectsVehicleWhenInspectionFails в FleetTest. 
Зависимость подменяется через конструктор: new Fleet(new AlwaysFailInspectionStub()). 
Это гарантирует, что транспорт не будет добавлен, и метод вернёт ошибку.

**Как подменяется зависимость.** `Fleet` принимает
`ITechnicalInspection` через конструктор. В тестах вместо реального
`ServiceCenter` подставляются заглушки:

- `AlwaysPassInspectionStub` - `inspect()` всегда возвращает `true`;
- `AlwaysFailInspectionStub` - `inspect()` всегда возвращает `false`.

Дополнительно `ServiceCenterTest` проверяет сам `ServiceCenter` без подмены.
Тесты (например, rejectsScooterWithTooLowFriendliness), которые проверяют, 
что устройство с простотой < 2 или энергией > 100.0 будет отклонено.

**Правило «для новичков»:**

Тесты в VehicleTest и FleetTest (vehiclesForBeginners_returnsOnlySuitableVehicles), 
проверяющие, что в выборку попадают только устройства с beginnerFriendliness >= 6.
